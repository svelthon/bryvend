# Patches applied to the vendored Brython

`brython_runtime.js` and `brython_compiler.js` are cut from one bundle, built
from Brython's master of 11 September 2026 plus two hundred and sixty-six proposed commits
(`metaclass-getattribute-args`, `iterator-setstate` and `getitem-binding` in two, as amended for their PRs), nine merged
upstream since (#3022, #2996, #2989, #2982, #3125, #3047, #3119, #3072, and master's `3afab4451`), and a hundred and
three of mine merged upstream between 12 September and 14 October that the bundle had missed, carried as master holds
them: the modulo and the floor division of a float, the concatenation and the slice of a list or tuple subclass, an
`__index__` as a subscript, `None` and the order of a union, `delattr` answering `None`, the sign and the padding of an
integer format, a `__call__` that is a descriptor, the arguments of the `Unicode*Error`s, a named escape in an f-string,
the docstrings of the builtins, and the like. Two of that span are left out, which master carries along with later
changes of its own: the module prefix of a `GenericAlias`'s repr and an explicit `__module__` kept in a class body, each
of which failed a test of the suite here. With **three** edits made in the file itself afterwards: the wrapper carries a
`/* BRYVEND patch, see BRYTHON_FIX.md */` comment, the only way to find it again in 1.4 MB; `@vite-ignore` *is* a
comment, so it finds itself, and the CommonJS export is a line that is no longer there. The integer format and the
`__call__` binding, two edits of the built file until now, are master's commits of the span above.

`unicode.txt` ships beside the bundles, as it is in Brython's `www/src`: the names of Unicode characters a `\N{BULLET}`
escape is read by, which a page fetches beside brython.js and a compiler under Node reads off the package.

The commits are Brython's own, proposed upstream and carried here while they
wait, which is what this project has always done rather than hold a fix back.
The one merged upstream is master's `18571ba0d` (#3022), a memoryview's item
decoded by its format and read from the end, which the slice commit below is
written against:

Wrapping the file works because `var` keeps its module scope inside a block, so
the 1.4 MB below is untouched: two added lines, top and bottom.

**Two `@vite-ignore`, and it was eighteen.** The other sixteen sat on
`$B.$import(...)`, which is Brython's own function and not a dynamic import, so
`vite:import-analysis` never looked at them; `$B.$import(` merely contains
`import(`. Measured by removing them and counting what the dev server says:
eighteen gives none, two gives none, none gives exactly two, at `import(ref)`
and `import(refs[0])`. They cost nothing at run time and sixteen edits to
re-apply at every re-vendoring.

**Both would be wrong upstream.**

The file wrapper answers a *second execution in one process*, a build tool
evaluating the same file in a module graph of its own, or a server rendering
after the compiler has run.
A browser loads the script once per page, so the guard protects nothing there
while changing the top-level shape of the file for everyone.

`/* @vite-ignore */` is a comment addressed to **one bundler**. It means nothing
to esbuild, to Rollup on its own, or in a browser. A build tool's annotation has
no place in an engine that is not built with it.

## Beside the file: Brython outside a classic script

`brython.js` was written for a `<script>` in a page. Run as an ES module, in a
page or under Node, it finds none of what that page gives it, and two modules
of Bryvend, `start/`, give it back. Not proposed upstream yet: they are the first
step for Brython to run under Node with nothing else, towards a `$ brython` as
there is a `$ python`, and the PR will come from them.

| Beside the file | What it buys |
|---|---|
| `start/page.js`, before the runtime runs | what the page of a classic script gives `brython.js`: `self` and `addEventListener`, which Node has not; `brython_path`, since `document.currentScript` is null in a module; `$B` as a global, which the code generator's `eval` resolves; and under jsdom, a process that says there is a DOM, the question `isNode` means to ask |
| `start/engine.js`, after it | the engine started once, as a page's `brython()` starts it, with `ipy_id: []` since the Python run here is compiled ahead of time; then, off a browser, the DOM stubs `brython.js` laid down taken back, which made every library that tests `typeof document` take the browser path on a server |
